## Core rule: a C compiler and CMake are the only build requirements

A fresh clone must build with nothing installed except a C11 compiler and
CMake (>= 3.15):

```sh
cmake -B build
cmake --build build
```

Everything else the build needs is either CMake itself or source that lives in
this repo and is compiled by this build. Concretely:

- **No** system packages: no `find_package`, `pkg-config`, Homebrew/apt
  libraries, or "install X first" steps. The only exceptions are the OS SDK
  itself (libc, `m`, `pthread`, platform frameworks such as Cocoa/Metal on
  macOS, `user32`/`gdi32` on Windows).
- **No** network at build time: no `FetchContent`, `ExternalProject`,
  `git submodule`, or downloads in CMake.
- **No** scripting languages in the build: no Python, Perl, Node, Lua, Bash,
  or `sed`/`awk` steps. If CMake can do it (`file()`, `string()`,
  `configure_file()`, `cmake -P`), use CMake. Otherwise write a small C tool
  and vendor it (see Tools below).
- The `Makefile`, if present, is only a convenience wrapper around the two
  commands above. Never put build logic in it that CMake doesn't also have.

If a change seems to need a new external requirement, stop and ask instead of
adding it.

## Dependencies: vendored with cdeps

All third-party code is vendored into the repo with
`cdeps` and committed.

- `deps.lua` — the spec: which repos, at which tag/branch, which files.
- `deps.lock` — generated by cdeps; pins commits and hashes. Never edit by
  hand.
- `deps/` — the vendored source. Committed. Never edit files here directly;
  fix upstream and re-vendor, or vendor a fork.

cdeps is a maintainer tool, not a build requirement: it is only needed to
add or update deps. Because `deps/` is committed, building never runs it.

```sh
cdeps add <user/repo>   # add a dependency (then trim files/subdir in deps.lua)
cdeps update [name]     # bump to the ref in deps.lua, rewrite lock
cdeps verify            # check deps/ matches the lock (run before committing)
cdeps remove <name>
```

Rules for choosing and using deps:

- Keep the set minimal. Prefer writing a small amount of code over adding a
  dependency. Ask before adding one.
- Prefer single-header / few-file C libraries. Vendor only the files needed
  (`files = { ... }`, `flatten = true`) rather than whole repos.
- Pin to a tag or commit, never a moving branch for release code.
- Single-header libraries get their implementation in exactly one translation
  unit, `src/deps.c`:

  ```c
  #define BASE_IMPLEMENTATION
  #include "base.h"
  ```

- Larger deps that ship a `CMakeLists.txt` are built with
  `add_subdirectory(deps/<name>)` and linked by target. Set their options with
  `set(... CACHE BOOL "" FORCE)` before the `add_subdirectory`, and switch off
  anything that would pull in system packages.
- `deps.lua` may use `dev = '..'` to vendor from a local checkout while
  developing a sibling library; the lock still records the upstream URL.

## Tools: vendored source, built by the same build

Code generators and other build-time tools live in `tool/<name>/` as C source,
vendored with cdeps like any other dependency (e.g. from `cbase/tool`). They
are compiled as part of the normal build, then run by CMake.

- Each tool has its own `CMakeLists.txt` that builds an executable and exports
  a CMake function that wraps it, e.g.:

  ```cmake
  add_subdirectory(tool/embedc)
  embedc_generate(INPUT  ${CMAKE_SOURCE_DIR}/src/gui.xml
                  OUTPUT ${CMAKE_SOURCE_DIR}/src/gui_xml.h
                  NAME   gui_xml TEXT)
  ```

- The wrapper uses `add_custom_command(OUTPUT ... COMMAND $<TARGET_FILE:tool>
  ... DEPENDS tool <inputs>)` so outputs rebuild only when the inputs or the
  tool change. Targets that consume the output `add_dependencies` on a custom
  target for it.
- Tools depend only on libc (and other vendored source). They must be
  standalone: no deps on the project they serve.
- Never call a tool from `PATH`. If a step needs a program, it is either CMake
  or a tool built from `tool/`.
- Generated files are written into the source tree next to their input and
  committed, so diffs show what changed and the code is readable without a
  build.

Available tools (vendored from cbase/tool; delete the ones not used):

- `embedc` — embed a file as a C byte array or null-terminated string.
- `sql2c` — generate C from SQL.
- `singleh` — amalgamate sources into a single header.

## Layout

```
CMakeLists.txt   the build
deps.lua         cdeps spec
deps.lock        cdeps lock (generated)
deps/            vendored libraries (committed, don't edit)
tool/            vendored build tools (committed, don't edit)
src/             project source
src/deps.c       implementations of single-header deps
```

## Writing C

- C11 (`set(CMAKE_C_STANDARD 11)`). Must compile cleanly with
  `-Wall -Wextra -Wpedantic` on Clang and GCC; treat new warnings as errors.
- Format with the repo's `.clang-format` (LLVM base, 3-space indent, 80
  columns, `int *p`). Run `clang-format -i` on files you touch.
- Use `base.h` rather than reinventing basics:
  - Fixed-size types: `u8`..`u64`, `i8`..`i64`, `usize`, `isize`, `f32`,
    `f64`.
  - Memory: allocate from an `arena`, not ad-hoc `malloc`/`free`. Use
    `arena_temp_begin`/`arena_temp_end` for scratch work. Lifetimes are
    tied to arenas, so functions that allocate take an `arena *`.
  - Strings: `string` (pointer + length) slices with `S("lit")` and
    `STR_ARG(s)` for `%.*s`; build with `string_builder`. Only convert to
    null-terminated (`string_cstr`) at API boundaries that need it.
  - `ARRAY_SIZE`, `UNREACHABLE()`, `PRINTF_LIKE` for format-checked
    varargs, `LIST(T)` for dynamic arrays.
- Naming: `snake_case` for functions, variables, and types;
  `UPPER_CASE` for macros and constants. Prefix public functions with the
  module name (`string_trim`, `sb_append`).
- Mark everything not used outside its file `static`. Keep headers small.
- Prefer plain structs, functions, and data over abstraction layers. No
  hidden global state unless it's genuinely process-wide.
- Handle errors at the point they occur: return a status / zero value and
  let the caller decide. `assert` for programmer errors, not for input
  validation.
- Comments explain why, not what. Match the comment density of the
  surrounding code.
- Avoid compiler-specific extensions unless gated behind a macro with a
  portable fallback (see how `base.h` handles `UNREACHABLE`).

## Before finishing a change

1. `cmake -B build && cmake --build build` succeeds from a clean `build/`
   with no new warnings.
2. Tests pass.
3. If deps changed: `cdeps verify` passes and `deps.lua`, `deps.lock`, and
   `deps/` are committed together.
4. Regenerated files are committed alongside the inputs that produced them.
5. No new system, network, or scripting-language requirement was introduced.
